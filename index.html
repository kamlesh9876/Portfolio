/approach

I Build. I Break. I Figure It Out.

Most of my learning has happened somewhere between "this should work" and "why the hell is this returning 401?"

01
01 / Core Principle

I Go Under the Hood

I don't like treating frameworks as magic boxes. When something breaks, I want to understand where it actually broke — the API contract, database, network, process, deployment environment, or that tiny line of code I was convinced couldn't possibly be wrong.

trace → isolate → understand
02
02 / Production Thinking

I Think Beyond "It Works"

Getting a feature running locally is only the beginning. I care about what happens after I deploy it — validation, persistence, concurrency, observability, and the things a real user will inevitably do that I never expected.

build → test → observe → improve
03
03 / AI Philosophy

AI, But Grounded

I'm interested in useful AI, not AI for decoration. I care about giving models the right context, constraining what they're allowed to do, and making their outputs reliable enough to actually trust.

context → retrieve → reason → respond
04
04 / Failure Engineering

I Design for Failure

Systems rarely fail where you expect. So I design for the moment everything goes wrong at once — invalid input, expired sessions, unavailable services, race conditions — so the system degrades gracefully instead of collapsing.

validate → recover → retry → fail safely
05
05 / Learning Loop

I Learn by Shipping

Tutorials teach you syntax; shipping teaches you judgment. Every project here taught me something the docs never would — usually at 2 AM, usually the hard way, and always written down so future me doesn't have to relearn it.

build → break → learn → repeat

understand deeply. build deliberately. fail gracefully. keep learning.

I'm a Computer Science graduate from Pune who became slightly obsessed with figuring out what happens behind the interface — how a request moves through a system, how data flows between components, and what happens when something inevitably breaks.

My journey hasn't been a straight line from "learn Python" to "become a backend engineer." I've explored different languages, built APIs and database-driven applications, worked with Linux and real-time systems, supported real-world software, and spent an unreasonable amount of time debugging things that looked completely fine five minutes earlier.

Somewhere along the way, backend engineering became the part I enjoyed most. I like software where there is something to reason about — not just whether a feature works, but why it works, how it fails, and what happens when the environment stops behaving like the happy path.

More recently, that curiosity has moved toward AI engineering. I'm especially interested in the intersection between traditional backend systems and LLMs: retrieval, RAG pipelines, model integration, structured outputs, and building AI systems that are grounded in useful information rather than simply generating convincing answers.

I'm still early in my career. And honestly, I like that.

There's a lot I don't know yet. That's also the part I'm most excited about. I'm here to keep building, keep breaking things, understand what went wrong, and come back with a better system.

Things I Built Because I Wanted to Know If I Could

Some started as ideas. Some started as assignments. Some started because I had no idea how difficult they would become.

DOC Analyser

RAG + Vector DB

Can I make an LLM answer questions from a document without simply making things up?

A document Q&A system using RAG, FAISS, LangChain and LLM APIs. Documents are split, embedded and indexed before relevant context is retrieved for generation.

The interesting part: The difficult part wasn't calling an LLM. It was deciding what information the model should actually see.
What it taught me: Retrieval quality matters just as much as generation quality. A smarter model cannot magically fix bad context.
Python RAG FAISS LangChain Gemini Groq

Online Code Editor

WebSockets + Full Stack

What if a browser could become a tiny development environment?

A browser-based code editor with real-time communication, syntax highlighting, session persistence and code execution.

The rabbit hole: Building the editor was one problem. Keeping state synchronized while multiple things happen at the same time was another.
What I learned: Real-time applications force you to think differently about state. You stop asking only "what is the value?" and start asking "who changed it, when, and what does everyone else know?"

Vedaz — Real-Time Chat

WebSockets + React

Build a chat application where messages don't disappear just because the server restarted.

React + Node.js + Express + Socket.IO + SQLite. Handles authentication, persistent messages, timestamps, typing indicators, online/offline presence, delivery states and real-time communication.

The part I actually cared about: Real-time UI is easy to fake. Making the state reliable is harder.
What I learned: WebSockets make communication instant. They don't automatically make your application correct.

Digital ID Management System

Full Deployment

A university needed a practical way to generate and manage digital student IDs. So I built one.

The system handles student information, digital ID generation, QR/barcode integration, PIN protection, print-ready output and administrative workflows.

The interesting part: This wasn't just about writing code. It involved deployment, Apache/PHP configuration, database changes, file handling, environment issues and figuring out what breaks when software leaves your laptop.

EMO — AI Persona System

Python + LLM Modes

What happens when one model has to argue, research, code, and small-talk — without sounding the same?

A cyberpunk-inspired AI persona system with dynamic modes for casual chat, deep research, code generation, and structured debates — tuned for high-signal, zero-fluff interactions.

The interesting part: Each mode changes what the model prioritizes — depth, structure, or speed — instead of treating every prompt the same way.
What it taught me: Prompt architecture is real architecture. Constraints and context shape behavior more than model size does.

Instead of showing you another list of technologies, here's how I think about the systems behind them.

The problem isn't "How do I call an LLM?" The problem is "How do I give it the right information at the right time?"

Documents → chunks → embeddings → vector search → relevant context → generation

The goal isn't to make the model know everything. It's to make it know what it needs.

Things That Broke Me (Technically)

Not from tutorials. From actually building things.

401 Unauthorized

Learned that having authentication code isn't the same as having a working session lifecycle.

"Works Locally"

Deployment introduced a completely different class of problems — runtime versions, native modules, environment variables and build configuration.

The Missing Column

A database schema and application code can disagree very confidently.

The Race Condition

Two things happening at the same time is easy to write. It's much harder to reason about.
